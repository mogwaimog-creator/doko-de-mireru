# シーズン台帳：省コスト更新方式（設計案）

更新日：2026-11-07。対象ブランチ：`work/four-ledgers-20261107`。本番への変更なし。

## 1. 既存の更新系統とは分離する
- シリーズ作品の配信情報：既存の日本時間06:00・18:00の更新を維持。
- 通常の作品詳細の配信情報：既存の24時間経過後、次のアクセス時に更新する方式を維持。
- シーズン・エピソード情報：別の保存領域 `doko:season:v1:tv:<id>:<season>` で管理。配信更新Cronには組み込まない。
- シーズン情報を見に来たアクセスだけを更新判断の契機とし、全作品・全シーズンの一斉巡回は行わない。

## 2. 鮮度の判定（提案・未実装）
- 初回：シーズンを開いたときだけTMDBの該当シーズンを取得。
- 放送予定・放送中：最終成功から7日以上経過し、次にそのシーズンが開かれた場合だけ更新候補にする。
- 完結済み：最終成功から90日以上経過し、次に開かれた場合だけ更新候補にする。手動訂正手段は別途用意。
- 「完結済み」の確定には作品台帳の放送状況や最終放送日などの信頼できる情報が必要。現行のシーズンレコードはエピソード日付しか保存しないため、日付だけで完結を断定しない。状態不明は7日側として扱うが、取得量の上限を優先する。
- 期間は運用上の仮設定であり、実測のアクセス数・TMDB呼び出し量を見て調整する。

## 3. 障害時・同時アクセス
- 保存済みデータがあれば、更新失敗時は最後の正常データを返す。
- 更新ロックを取得した1リクエストだけがTMDBに問い合わせ、他のアクセスは保存済みデータを返す。
- 成功した応答を検証してから更新し、エラー応答・不完全なデータ・シーズン番号不一致では上書きしない。
- 初回登録の `SET NX` は維持。更新は別のロック付き経路で実装し、書き込み失敗時は旧レコードを維持。
- 同じシーズンの連続失敗時は再試行間隔を置き、アクセス集中でTMDB呼び出しが連発しないようにする。

## 4. Redis容量と費用の安全策
- 現行の配信キャッシュにある `LEDGER_WRITES_RESUME` 制限を尊重する。シーズン台帳の新規保存・更新を無条件で有効にしない。
- **重要：現在の試作 `api/_season-ledger-redis.js` は `LEDGER_WRITES_RESUME` を確認していない。** 本番有効化前に保存側のガードが必須。
- 保存件数・データ量・TMDB呼び出し回数・失敗数を確認できるようにする。
- 追加課金や容量上限の懸念がある場合は更新を停止し、既存データ表示を優先する。
- 本番Redisへの接続・書き込み・デプロイは明示的な承認があるまで行わない。

## 5. 次の実装順
1. 更新判定だけを純粋関数として作成し、7日・90日・不明・時刻異常をオフラインテスト。
2. 保存禁止フラグと書き込み容量上限のガードを設計・テスト。
3. ロック、失敗時の既存データ優先、再試行抑制を模擬テスト。
4. 実ブラウザ・実環境の費用影響を確認し、ユーザー承認後に限定切替。
