## 3. Upstash：転送量・保存容量

バックアップをVercelのAPI経由で配信せず、PC側/隔離環境のツールで取得・ファイル化する計画です。PCへのファイルコピーやローカル復元をUpstashへの再送として数えません。旧復旧用のアップロードと、復旧後の照合ダウンロードは含めます。

転送の式は、`バックアップ受信＋旧復旧送信＋復旧照合受信＋最小投入/照合＋通常運用＋日次更新`。さらに試算には通信形式等の**25%の余裕係数**を掛け、残8GBの80%＝**6.4GB**までとする提案です。

例として、DUMPの原バイト列も201MBだった場合だけ、Base64は約268MB。キーや明細の仮の余白を加え、バックアップ・旧復旧送信・照合受信を各270.2MBと仮置きしました。投入/照合2MB、検証10MB、その他の残期間転送500MB、日次更新0.31702MB×31日も加えると、余裕係数を掛ける前が約1.332GB、掛けた後が**約1.666GB**です。

この仮例は残8GBに収まりますが、**画面の保存容量201MBとDUMP・JSON・実通信量は同じではありません**。実際の出力サイズ、最大キーの大きさ、形式、ヘッダー、プロバイダーの集計方法は未測定です。転送が足りるという本番判定には使いません。

容量は、初期化前は旧201MB、バックアップはRedis外へ保存。承認後の初期化後は新台帳本体・必要索引・キャッシュ・履歴・余力だけです。新5台帳の実量は未計測で、過去の小さい試験データを本番容量と扱いません。新方式の運用余力込み175MB（250MBの70%）以内という提案基準で実データを照合します。現49MBの空きへ旧全件の複製を入れる計画にはしません。

Build CPUの単位は、作業時間に利用CPU数を加味したものです。58時間を画面上のビルド待ち時間の合計と同一視しません。[Vercelのビルド仕様](https://vercel.com/docs/builds/managing-builds)を参照しています。
