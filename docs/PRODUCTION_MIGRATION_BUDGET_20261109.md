## 2. 量り方

**今回は実行しない将来手順です。** 本番に接続する前に計測範囲・通信・費用・権限を確認し、別途承認を得ます。まずは利用者の画面メモと安全な実データコピーで計算します。

1. 公開中の版・実保存形式・対象件数・旧キャッシュ・他アプリの共用を棚卸し。未使用と確認できないものも現使用量に含める。
2. 元値/保護情報を保存したコピーを、無料/上限確認済みの隔離環境で変換。人物の出演作が多い例、全話が多いTV、長い原題、複数監督/多数出演者、手動欄/ロックあり、エラー保持ありを含める。
3. JSONのファイル容量だけでなく、保存後の本体・キー・メタ・索引/登録一覧・互換コピー・進捗/監査/通知を別々に量る。Redis内の集合は全体を量る設定を用い、プロセス/断片化等の余裕も確保する。
4. 索引は文字数・原題・共通する検索要素で変わる。実データから実際に構築して量り、短い題名だけの平均を全件へ適用しない。型/文字数の上限で取り込めないものは、切捨てず移行不能として隔離する。
5. 区分ごとの件数と平均/最大/大きい側の分布を記録。推定を使う場合は保守的な上側と誤差を示す。未観測の種類や件数不明が残れば「未計測」とし、開始判定をしない。
6. バッチごとの増加、失敗/再開、全件復元用コピー、保存期間中の履歴、移行期間の通常成長を追加する。実プランの表示と低負荷な範囲で突合する。全件に対する重い計測を日常処理へ常時入れない。

## 3. 容量の式

| 記号 | 内容 |
|---|---|
| U | DB全体の現使用量。旧台帳・他用途を含む |
| D | 新5台帳の追加本体量 |
| I | 新検索索引・索引文書・ID一覧 |
| L | 必要な旧形式の読取専用コピー。旧本体と二重になる分 |
| M | 版番号・エラー/制御・監査・通知等 |
| H | 新しい日次履歴（保存日数×日ごとの量） |
| G | 見積期間中の通常成長 |
| B | Redis内に置くバックアップ原本。PC/作業環境ファイルだけならRedisのBは0だが、ファイル容量・送信量は別 |
| R | 検証/復元用の追加領域。原本とは別に必要 |
| A | 更新中の大きい値・失敗保持・処理中状態・計測誤差/余裕 |
| Q | 確認できた容量上限 |

- **移行後（旧データを保持）**：`U + D + I + L + M + H + G`
- **移行中ピークの上側**：`U + D + I + L + M + H + G + B + R + A`
- **増加率**：`(予測値 - U) / U × 100`。U不明なら計算しない。

旧削除による減少は一切見込みません。新旧で同じ実体を再利用できる量も、確認前に差し引きません。バックアップと復元を何個並べるかも先に決め、コピーを増やす前に再計算します。

## 4. 停止基準の提案

**上限や課金条件が不明なら、割合の計算より先に停止。今回この仕組みを本番へ設定/接続していません。** 現在の実装には以下の契約残量に連動した自動停止は未実装です。

| 段階 | 提案する条件 | 対応 |
|---|---|---|
| 開始不可 | Q/現使用量/超過時の動作/ピークの主要成分が不明。実データの種類に欠ける。実行時間・操作互換性未確認 | コピー/起動を始めず、見積もり/照合を先に行う |
| 開始可能の候補 | 保守的に見たピークがQの**70%以下**で、月内の各費用枠も下記の範囲 | これだけで実行承認とはしない。少数から、範囲と停止担当を決める |
| 一時停止 | 実使用量、または次バッチ＋残すべき復元余裕込みの予測がQの**80%以上**。予測以上の増加、表示遅延で残量が分からない | 新移行・新更新・追加コピーを止める。確認済み旧値の読取を保持し、原因を調べる |
| 緊急停止 | Qの**90%以上**、保存拒否、記録の自動追出し、保存結果不明、二重起動、保護情報差分 | 新規書込みを止めて通知/記録。データを削除したり、勝手に有料へ変更したりしない |

70/80/90%は契約規定ではなく、誤差・通常増加・切戻しの余地を残すための提案です。例えば**仮に**Q=100MBなら、ピーク70MB以下を開始候補、次バッチで80MBに達する前に停止、90MBは緊急扱いです。この100MBは実契約の値ではありません。

反応が遅い使用量表示、非常に大きい1件、他用途の急増がある場合は、もっと手前で止める値が必要です。旧値の読取りが可能でも、容量不足のまま旧更新を自動再開しません。削除は別承認、本番への接続/実施も別承認です。

## 5. 通信・実行・取得の見積もり

### Redis

新方式の通信の基本式（全N件が更新必要、正常成功）は、`2N + 2R + 2K + O`。

- N：重複除去後の作品数
- R：進捗を引き継ぐ内部処理の回数
- K：12件程度のまとまりの合計数（現開発設定）
- O：監視/状態記録など。正常監視は現在の構成で概ね2通信

266件では、一括試験R=1、K=23が580通信（監視別）。標準24件分割はR=12、K=23で602、正常監視込み604という**コードからの推計**です。現在の旧コードは同じ266件なら269通信という計算。旧開発実装1,330回から減った結果と、現行旧方式との比較を混同しません。

月内見積もりは `既に使った量 + 残りの日数の通常閲覧/検索/更新 + 移行/検証/バックアップ/再開/監視の追加量`。EVAL内部の操作やまとめ読取が契約上どう数えられるかを確認します。RPCやローカルRedisの内部操作数を、そのまま請求数にはしません。

検索の最初のページの例は4通信、継続ページでは要素選択を省けますが、候補の多い語では追加バッチが必要です。索引作成/再作成、原本の読み出し、復元・全件照合も別加算です。送信引数だけでなく応答・通信方式の上乗せを含む量で確認します。

### Vercel

実行数は `閲覧/検索等からの公開API実行 + 初期HTML生成 + 定期起動 + 別起動での再開 + 監視/通知用実行 - 確認済みキャッシュ効果`。Redisへの4通信をVercelの4実行と数えません。内部12回と、別々の12実行も区別します。

回数だけでなく処理時間・メモリ・CPU・転送量が必要です。全266件が各6.5秒待つ概算では、新しい並列3なら約576秒で、1回の短い実行へ無条件に収まりません。実行上限より前に止めて残りを安全に起動できることを、実遅延/Redis待ちも含めて検証します。現在の240秒等は絶対終了保証ではありません。

### TMDB

保存済みデータの移行コピーは、原則新しい取得をしません。欠損/古い値はまずそのまま未確認として残し、取得で勝手に補いません。通常運用では、13シリーズ266件の日次、シリーズ外の24時間経過アクセス、人物60日、期/話7/90日、初回登録が別々です。人物の各出演作の配信まで再取得しません。

失敗/未保存の復旧2回等は隔離暫定。厳密な上流1回実行は、取得後・保存前に停止すれば保証できません。取得予定の上限と止め方を確定してから本番に使います。

### 月内予算の提案

通信数、転送、Functionsの処理量等について、**残り日数の通常利用と1回分の安全な復旧を加えた月末予測が、確認できた追加料金なしの枠の70%以内**を開始候補とします。80%へ近付く/予測を超える場合に新移行を停止する案です。容量と同じ割合でも同じ単位ではないので、項目ごとに判定します。

「請求額通知」だけを課金停止と扱いません。自動追加料金を止められるか、上限超過時の動作、他アプリ/チーム全体の使用量、集計の遅れを確認します。契約上の追加料金なし枠がない/不明、または追加料金の可能性が残る場合は、実行せず利用者へ事前相談します。

本番容量・実通信・Vercel負荷・費用額は、現段階では**未確認**です。
