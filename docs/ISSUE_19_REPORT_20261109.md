## 実装・試験したこと

- 配信更新を32作品単位へ変更。取得前に実行予定を永続記録し、配信値と進捗を1回で原子的に保存。複数ワーカー、個別アクセス更新との相互排他、期限切れ所有者の拒否、保存値の比較、共通停止確認を残しました。保存応答を失った場合も記録を見て再取得を避け、繰返し障害時は取得回数上限で停止します。
- 新しい復旧フラグではシリーズAPIと詳細が旧配信の互換コピーを読みません。比較表と13シリーズは同じ新配信値を参照。フラグ無効時の既存経路と本番ガードは維持しました。
- 一般検索は1〜2個の検索APIだけを使い、検索結果の各作品の詳細・配信を一斉取得しません。64個の期限付き検索キャッシュを再利用し、巨大な全文検索索引を復旧の必須条件から外しました。映画/TVの同じ数字は別扱い、人物検索も作品ごとの配信取得なしです。
- 未登録作品の詳細、未登録人物のプロフィール/出演作、未登録TVシーズンはアクセス時に取得・再利用する開発経路を追加。固定情報キャッシュに配信を保存せず、配信だけは共通台帳を読みます。既存手動データがある場合はその読取り経路を優先します。
- 全形式のバックアップ、SHA-256、件数、期限の保持、新しい隔離キーへの復元を追加。string/hash/list/set/zset/streamとバイナリ値を試験。ローカルファイルへの保存・再読取り・復元も実施しました。
- 最小投入器はJSONをそのまま保持。全対象の事前衝突確認、バッチ内の再確認、全件再読取りを実施。同一ファイルの再開は可能、既存値が異なれば停止し、手動欄・ロック・多数の出演者を勝手に削りません。
- 外部へ接続しない費用・容量の開始判定器と、一括入れ替え手順書を追加。情報不足は不合格とし、旧データ復旧1回分の余力も含めました。

新経路は `DEV_LEAN_SERIES_ENABLED=1` などの開発フラグと127.0.0.1限定の橋渡しを使います。**本番で使える認証情報・接続先・自動起動は未接続**で、そのまま本番完成版とは扱いません。

## Redis通信の比較

同じ266 ID、初期値なし、日本配信0件の正常な試験応答、同じローカルRedis 7.2.6で比較しました。旧方式は実際の `api/update-streaming.js` を隔離された接続先へ差し替えて実行しています。

| 指標 | 旧方式 | 新バッチ方式 |
|---|---:|---:|
| 更新本体の通信往復 | 269 | **20（92.6%減）** |
| Redis内部のLua内命令も含む操作数 | 271 | **126（53.5%減）** |
| 外部配信取得 | 266 | 266 |
| 送信引数の合計 | 35,150 bytes | 315,777 bytes |
| 応答JSONの合計 | 2,400 bytes | 7,076 bytes |
| ローカル完了時間 | 約453ms | 約82ms |

新方式を既存監視へ接続した場合はGET/MSETの2往復・2命令を加え、**22往復・128命令**です（接続コードからの算定）。前の開発方式の約604往復は、24作品ずつの複数内部起動と監視を含む推計で、今回の旧本番269との同条件比較とは区別します。

**転送量は減っていません。** 再開・重複防止の進捗、レンタル/購入、取得日時・失敗状態も保存するため、送信は旧方式の約9倍。新方式の引数＋応答は約0.323MB/日、30日で約9.69MBの試験値です。HTTP/TLS/Redis通信形式と実際の配信件数は別に加算します。通信回数だけを減らして「費用が同率で下がる」とは説明しません。進捗差分だけの送信等は今後の改善候補です。

Redis CLI試験用の接続時HELLOはアプリ命令数から除外し、JSONに別記（21回）しています。**UpstashがEVAL本体・内部命令をどう集計するか、実際の請求単位は未確認**です。パイプライン化だけで課金対象命令が減るとは仮定していません。

生データ：[Redis比較](ISSUE_19_REDIS_BENCHMARK_20261109.json)。タイミングはローカル模擬応答であり、実TMDB・Upstash・Vercelの速度ではありません。
