# 作品詳細の1リクエスト化：実装前の確認事項（PR #13）

## 現状（コード確認）
- `detail.html` の `loadMovie()` は `/api/search?id=...&type=...` を `cache:"no-store"` で取得する。静的HTMLに固定情報を埋め込んでも、この呼び出しは残る。
- `api/search.js` の映画・TV詳細は `metadataWithLedger` と `getDetailProviders` を内部で組み合わせ、固定情報・配信情報をまとめた1レスポンスとして返す。
- `api/_detail-providers-cache.js` は約24時間のオンデマンドキャッシュ、同時更新ロック、取得失敗時の旧データ利用を備える。シリーズの6時/18時Cronとは別。
- 静的ページの `readFixedDetail` は埋め込み固定情報を読むが、現行の画面描画にはまだ利用されない。

## 採用候補（未実装）
静的HTMLの固定情報が**検証済み**の場合だけ、既存の表示用データのうち配信関連項目を、**1回だけ**呼ぶ新しい配信専用APIから補う。固定情報が欠損・不一致なら、既存の統合APIへ**1回だけ**フォールバックする。配信専用APIを呼んだ後に統合APIを追加で呼ぶ通常経路は設けない（エラー時の動作は別途設計・検証）。

## 必須の設計ゲート
1. 作品ID・movie/tv種別の厳密照合。異なる作品の配信情報を結合しない。
2. 見放題・レンタル・購入・サービス別リンクを現行表示と同じ形で返す。データ欠損を「配信なし」に置き換えない。
3. 現行のRedisキー・24時間更新・排他ロック・stale時挙動を維持する。6時/18時Cronは変更しない。
4. `WORK_LEDGER_ENABLED` の本番値と `extensions.tmdbDetail` の実データ充足率は未確認。実際の表示一致・キャッシュヒット率・Function回数削減は未測定。
5. ブラウザの通常の詳細表示は最大1回のAPI要求。検索や別機能の呼び出しは別途棚卸しする。
6. 既存URL、検索エンジン向けメタ情報、503時の表示、セキュリティ制限を維持する。
7. まずオフライン契約テストと試験用HTMLで検証。本番へのルーティング切替・Cron変更・有料試験は行わない。

## 未解決
配信専用APIのレスポンスは現行の `getMovieDetail` / `getTvDetail` が固定情報から導出するフィールドも含むため、現行の正規化ロジックを安全に再利用する設計が必要。単純に配信プロバイダ配列だけを返すと表示が欠落するおそれがある。これが次の実装上のブロッカー。
