## 検索の仕組みと保護

索引は題名/原題・人物名/原名をNFKC等で正規化し、1文字/2文字の検索要素をRedisの辞書順索引へ保存します。候補を本体で照合してから表示するため、索引の余分な古い候補を現在の題名として出しません。新しい索引候補を本体保存より前に追加し、本体・メタ・索引文書を同じMSETで保存、古い候補はその後に除去します。

Redis Luaはエラー時に全操作が巻き戻るとは扱っていません。保存前の異常では本体を変更せず、保存後の除去障害では余分な候補が残り得る設計です。保存結果不明/索引障害は共有停止として扱い、再確認します。候補を常に本体で照合することと、通常ライターをこの保存経路に統一することが安全性の前提です。

1回の候補読取りは最大32件。最大512候補と読取り量の予算で区切り、カーソルで続けます。最初に最大16個の検索要素の件数を調べ、候補が少ないものを選びます。本体の読取りは1バッチ約512KiBを目安に区切り、単体1MiBを超える保存値は安全側で拒否。1リクエストの本体読取りは2MiBの予算を超えたところで終了します（最後の1バッチ分、最大約1MiBの超過余地）。全件を1回のMGETへ渡しません。

予算に達して0件でも、続きがあれば最終0件とは扱わず「続きを検索」を表示します。カーソルは検索語と区分に結び付けます。深いページはページ番号だけでなくカーソルが必要です。同時更新中の全ページは厳密なスナップショットではなく、再検索が必要になる場合があります。

ブラウザ検証で、保存済み検索の追加ボタンが詳細条件検索用の処理につながる問題と、「すべて」検索の追加取得で区分が抜ける問題を見つけました。保存済み検索を通常の継続処理へ接続し、区分/カーソルを保持するよう修正。PC/モバイルのデザイン、シリーズの順番や文章は変更していません。人物候補画面の従来の先頭20件表示は維持し、APIには継続カーソルがあります。人物候補の画面上の追加表示は残作業です。

## 管理・バックアップの安全条件

- 確認表示は本体/メタの版番号・エラー・確認済み状態・項目ロック・ハッシュを返します。手動編集は観測した版番号を要求し、作品・SEO・検索索引へ反映。未解決エラーを残す確認を拒否し、ページ固有欄を保持します。
- 共有停止は自動解除しません。解除計画は疎通検査後に作成し、停止理由の対象を自動追加。値/メタ・停止状態が変わる、leaseが残る、計画が失効する場合に拒否します。確認と適用は分離し、`--reviewed`を要求します。SHA256は破損検出用で、第三者の認証署名ではありません。
- バックアップは共有停止とワーカーの終了を要求し、読取後も値が変わっていないか再確認します。本体最大5,000キー、メタ込み10,000キー、ファイル16MiBまで。読取りを小分けにし、ファイルは0600、既存ファイルは上書きしません。
- 復元は**新しい隔離名前空間だけ**。キー/スキーマ/ハッシュ/失効時刻を検査し、全件照合前は`incomplete`、完了後だけ`verified`。元データも失敗した領域も自動削除せず、TTLを延長しません。復元した作品・SEO・人物を実際の保存済みリーダーで読む試験も通しました。
- 大きい人物データの試験では、OSのコマンド引数長を超えないよう、テスト用クライアントにループバック限定のRESP通信を追加しました。実Upstash用クライアントへ接続したものではありません。
