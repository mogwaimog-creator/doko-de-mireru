## 2. 何を保存・置換・残すか

置き換えるのは、十分な照合と承認後の「新しい画面/更新処理の参照先」です。旧データの削除・上書きではありません。本番用の新しい保存名はまだ確定しません。`doko:dev:`を機械的に本番名へ変えるだけの移行は禁止する設計案です。

| 現在の情報 | 新しい参照先の案 | 必ず残すもの・開始条件 |
|---|---|---|
| 旧作品 `doko:work:v1:movie/TV:ID` | 新作品＋必要な表示互換情報＋検索索引 | 元の完全な値・版・保存日時・出所を保存。現在の縮小変換だけで一括切替しない |
| 手動記入、確認済み状態、個別ロック | 同じ意味で働く新しい保護情報 | 元値と保護対象の一覧を保存。ロックの対象や効き方が変わる場合は停止。移行を理由に「確認済み」を解除/新規付与しない |
| 特集ごとの紹介・順番・見出し・ポスター等 | ページ固有欄/既存ページを維持 | `pageExtras`、所属・関連、ページHTMLの手動欄を別々に照合。見る順番の所属を正式コレクションと推定しない |
| 共通配信 `doko:watch:v3:` | 新配信台帳へ読取先を段階切替 | 旧正常値・取得時刻・対象期間を保存。見放題しか持たない値からレンタル/購入0件を作らない |
| 旧詳細配信 `doko:detail-providers:v1:` | 新配信との時刻/区分別の互換読取 | より新しい正常値を古い値で隠さない。取得失敗/未来日付/時刻不明は別扱い。旧コピーを残す |
| 人物 `doko:person:v1:`、既存 `v2:` 等 | 確認した実形式から新人物＋索引 | 同じv2名でも中身が同じと仮定しない。人物本文・全出演作・独自欄・旧更新日時を原本に残す |
| 期別の旧シーズン記録 `doko:season:v1:...` | 同一TV単位で統合したシーズン台帳 | 全期を数え、特番・0期・全話・各取得日時を照合。未取得を空リストにしない |
| 検索カタログ | 新索引を再作成し、参照先のみ切替 | 旧カタログを保持。索引は作品/人物本体から作る派生情報で、本体の代わりにしない |
| 作品/特集の公開SEO・正規URL | 新SEOを比較後に適用 | 現行HTMLとURL一覧を保存。手動SEOの未確認上書き、不要なURL変更をしない |
| 旧進捗・エラー・処理中のロック | 新方式は新しい領域に作成 | 旧履歴や他の処理のロックを削除しない。同日旧進捗がある新方式は現在拒否するため、別途切替計画が必要 |

### 手動情報の保護を証明する方法

移行対象ごとに「元の保存場所、元値、手動か不明か、確認済みの意味、ロック対象、特集の所属/固有欄、新しい保管先、新しい読取/表示/更新での効き方」を一覧にします。手動か判断できない値は、自動取得の値と決め付けず保護対象にします。未知の欄が1つでもあれば、保存先と利用方法が決まるまでその対象の切替を止めます。

原本は完全な値のまま別ファイルに保存し、復元照合します。現管理CLIは開発の新形式用で、旧本番の全5台帳を原本のまま書き出して復元できると実証したものではありません。既存のバックアップ検査スクリプトも、原本の取得済みを意味しません。現在の「互換コピー」は配信付加情報を除く加工コピーなので、完全な原本バックアップの代わりにはなりません。新台帳に移せない欄は原本/旧読取経路を維持し、利用者が見る情報を減らしてから解決する順序にしません。

比較は、文章/題名の値、所属と順番、確認済み件数、各ロックの対象と内容、エラー、movie/TV区別を対象にします。保護情報は**差分0件**が合格条件案です。IDが照合できたことを、手動文章や配信の確認済み認定に流用しません。

### 現変換で止める具体例

コードの純粋な変換例では、出演者10人→8人、監督2人→1人でした。`collectionId`のロックは新しいコンパクト形式に対応項目がなく残らず、`commonNotes`・確認の個別根拠/メモ・関連情報も新作品本体には入りません。`pageExtras`は保持されました。ただし関連情報等は旧互換コピー経由で使う箇所があり、「新作品本体にない＝原本から削除してよい」ではありません。

また人物の紹介文4,000文字/作品名200文字等の制限、シーズン/話の絞った項目、複数の旧形式を、手動情報に対する無損失変換と扱えません。元に作成日時がないときに初回登録日時を推測したり、コピーした日時を正常取得日時に置き換えたりしない仕様が必要です。

現在の作品取込関数は平らなv1形式を対象とし、作品・SEO・期情報等のどれかが既にあれば保護して止まります。デモの`fields`内に値を持つ形式、人物/期別旧形式の一括移行、部分移行済みデータの安全な統合/再開は別途必要です。既存値を消してやり直す方法を採りません。

## 3. 旧方式との負荷比較

本番の実測ではなく、現在のコードからの計算と既存ローカル実測を分けます。実行中の本番が同じ版かは未確認です。

| 266作品が全件更新必要で正常終了する条件 | Redisへの通信回数 | 根拠 |
|---|---:|---|
| 現在の旧更新コード | **269** | 計算：全体ロック1＋まとめ読取1＋266保存＋解除1 |
| 新しい日次処理を一括で1回呼ぶ試験 | **580** | 保存済みのローカル実測。Lua内部込み2,724操作 |
| 新しい標準24件分割（内部12回） | **602** | コードからの推計：作品532＋進捗46＋名簿/取得権24 |
| 上記＋正常監視 | **約604** | コードからの推計。旧269より約124.5%増 |

実際の旧更新対象は271件なので、同条件の旧通信は274回という計算です。新しい13シリーズ対象266件と条件が違うため、削減率として比較しません。残る `tv:93741`、`tv:237512`、`movie:335797`、`movie:862`、`movie:808` は削除せず、一般作品の24時間方式への扱いを確認します。

以前の1,330→533/580という削減は**過去の開発実装同士**の比較です。今回の旧269回は現在の旧更新コードの計算であり、混ぜて費用削減を主張しません。EVAL/まとめ読取の実課金単位はUpstash側の確認が必要です。一括試験の送信引数390,835 bytesも、標準分割や月全体の転送量ではありません。分割ごとの名簿再送、既存値の再読取り、応答を加えて見積もります。

TMDBは旧コードなら同条件で271回、新13シリーズなら266回/日が基本。旧方式の同じ期間の正常値は再利用されるので、旧方式が無条件に1日2回全件を取得すると仮定しません。新側の未保存復旧上限2回は隔離暫定で、最悪532回/日に加え、一般作品・人物・期/話・初回登録が別途あります。移行コピー自体は保存済み値を使い、原則TMDBを取得しない計画です。

Vercelでは、Redis通信回数を関数の実行回数と同じ数にしません。新方式の「内部12回」も必ずしもVercelの12実行ではありません。1回の関数内で続けるか、別の起動で再開するかが未確定です。現在の経過予算は各内部処理へ残時間を強制伝搬しないため、指定秒数が絶対の停止時刻とは扱えません。最長遅延/Redis待ちを含む実行上限の試験が必要です。

作品/人物検索の例は読取応答125,175→946 bytesですが、初回通信は2回→有効化確認込み4回へ増えます。人物初回保存は前回の4通信/内部13操作→索引込み4通信/内部18操作。索引は容量・更新操作・CPUを増やします。SEOを最初のHTMLから返す本番方式やキャッシュ次第では、ページごとの実行も増え得ます。月の実行数・処理時間・転送/課金は未計測です。

## 4. 二重更新を防ぐ切替手順案（今回は実施しない）

1. **起動元の棚卸し**：Vercel、GitHub、外部の定期呼出し、手動実行、ページアクセスによる更新を列挙。リポジトリの設定はUTC21時＝翌日JST6時の1件です。資料にある旧18時設定が稼働中か、別サービスにあるかは未確認。実ログと公開中の版で判断します。
2. **検証はコピーで行う**：新側の外部取得・本番書込み・自動起動は無効のまま、ID/手動情報/索引/表示を照合し、容量上限と停止条件を確定。
3. **別途本番承認後に旧書込みを止める**：定期起動だけでなく、旧ページ/API経由の書込み、人物/期の更新、手動入口も対象。現在の新側共有停止は旧更新コードを止めません。既存の保存凍結設定が配信定期更新まで止めるとも仮定しません。
4. **実行中処理を排出する**：旧/新の全体・作品別の処理中状態と実行ログを確認。期限や所有者を確認せずロックを削除しない。旧と新ではロック名が違い、両方有効にするだけでは二重取得を防げません。
5. **停止時点のバックアップ/最終差分コピー**：取得日時・保護情報・件数と一致を照合。処理途中・同日の旧進捗は推測して成功扱いしない。原則、切替当日は新しい再取得を始めず、次のJST6時から新方式1系統だけにする案を検討。
6. **読取を少数から切替**：鬼滅の刃/比較表を同じ共通読取に保ち、13シリーズ、詳細、検索、人物、期、初期SEOを確認。画面/容量/費用/失敗を監視。
7. **新更新だけを開始**：同一の実行責任者/切替設定で1系統を選び、並走期間を作らない。原本は残す。
8. **異常時の戻し方**：まず新起動/新書込みを止め、進行中処理を確認し、旧読取へ戻す。旧更新の再開は新処理の終了と容量の余裕を確認後。新しい停止制御だけで旧/新の両方を止められるとは扱わない。容量不足時は旧更新も無条件で再開せず、旧正常値の読取を保つ。削除/プラン変更で自動解決しない。
