### 公開前に解決すべき技術課題
1. **更新処理は未接続**：`api/search.js` が `makeSeasonSearchBranch({fetchJson,apiKey})` を呼び、`refreshRecord` を渡していない。ロック付き更新処理の模擬テストが合格していても、本番で更新されるとは言えない。
2. **保存禁止時のキャッシュミス**：`getCachedSeason` は保存禁止時に取得結果を表示できるが、Redisへ保存できない。次回の非同時アクセスでは再びTMDBへ取得し得る。公開フラグをONにするだけではAPI負荷削減を保証できない。
3. **配信情報などの応答差**：旧 `getTvSeason` は `title`/`poster_path`/`air_date`/`episode_count`/`streaming`/`rental`/`purchase` を返す。新 `seasonResponse` はこれらを返さない。現行 `detail.html` の `renderEpisodes` は主要項目だけで描画できるが、他の利用箇所の全数監査は未完了。
4. **Upstash RESTでのLua実接続未検証**：`api/_redis.js` は配列コマンドをREST POSTする。更新ロック実装の `EVAL`、戻り値、タイムアウト、権限、料金は模擬テストのみで、実環境での動作は未確認。
5. **更新周期の完成判定**：`status` は初回保存時 `unknown`。現在のTMDBシーズン取得処理だけでは `completed` を設定していないため、完成作品の90日更新周期は自動適用されない。
6. **シーズン0の扱い**：新ルートはシーズン0を許容するが、既存 `api/search.js` は `season` を最小1に正規化している。仕様を統一する必要がある。
7. **CDNと更新鮮度**：`api/search.js` は通常レスポンスにCDN 300秒と stale-while-revalidate 600秒を設定している。新方式で更新を有効化した場合の実際の鮮度・エラー応答・キャッシュ設定はブラウザ/HTTPで確認が必要。
