## シリーズ閲覧時の06時／18時更新：安全設計（実装前の確認事項）

**現状の事実**：`api/series-watch.js` は保存済み情報を `MGET` で一括取得するだけで、TMDBへ通信しない。共通キャッシュの更新は `_shared-providers.js` 経由の作品別詳細APIでのみ発火する。シリーズ閲覧だけで更新されるとはまだ言えない。

### 提案する更新方式

1. **読む処理と更新する処理を分離**：ページ表示は今までどおり `/api/series-watch` で一括取得する。更新のために全作品をページ側から個別リクエストしない。
2. **ページアクセスをきっかけに更新候補を選ぶ**：保存データの現在のJSTウィンドウと照合し、期限切れの作品だけを対象にする。新鮮な作品は絶対に再取得しない。
3. **一度のアクセスで更新する作品数を制限**：最初は**最大1作品**とする。47作品を開いた瞬間に47回TMDBへアクセスする実装は採用しない。
4. **同時アクセスの排他と失敗抑制**：作品単位の `SET NX EX` ロックと失敗クールダウンは既存 `_shared-providers.js` を再利用する。さらにシリーズ単位の更新予算を設け、閲覧者が増えても更新対象が無制限に広がらないようにする。
5. **レスポンスを待たせない**：更新をページの描画完了条件にしない。Vercel関数がレスポンス後も実行できると仮定せず、更新が完了するリクエスト経路を別途検証する。
6. **失敗は配信なしと区別**：取得失敗・ロック中・Redis障害では前回の配信情報を保持し、更新未確認と表示する。自動更新は維持し、手動の「再確認」は補助操作とする。
7. **新旧形式の競合を解消**：旧 `doko:watch:v3:` と新 `doko:provider-window:v1:` のどちらが新しいかを `checkedAt`／`lastSuccessfulAt` で比較する。旧キャッシュを無条件に上書きしない。
8. **段階的な有効化**：本番で既存動作を変えない初期値OFFのフラグで保護し、モック負荷テスト→プレビュー実データ→本番承認の順に進む。

### 実装時の合格条件

- 06:00直前は更新ゼロ、06:00以降の最初のシリーズ閲覧で更新候補が生まれる。18:00でも同様。
- 作品数が47件でも1リクエストあたりのTMDB更新は1件以下。同時100閲覧を模したテストでも更新数が予算内。
- Redis接続失敗・TMDB 429/500・タイムアウト・保存失敗でも「見放題なし」と誤表示しない。
- ロゴ表示・作品順・編集文章・スマホ表示に変化がない。
- 本番フラグをOFFに戻せば、即座に既存の読み取り専用経路へ戻る。

**残る判断点**：最大1件/閲覧だけでは、閲覧の少ないシリーズの全作品が同じ更新窓内に更新される保証はない。全作品を必ず06時／18時に更新する要件を厳密に満たすには、アクセス起点だけでなく、費用上限を守るスケジュール型の更新も必要になる。これは既存の「最初のアクセスで更新」方針と区別して検討する。
