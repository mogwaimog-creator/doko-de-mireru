## コマンド数と所要時間

N＝旧DBの全キー数、S＝1回の全走査に実際に必要だったSCAN回数、M＝投入対象レコード数、C＝ceil(M/32)。SCANのCOUNTは件数保証ではありません。以下はRedis内部のLua命令も含めた保守的比較で、Upstashの実課金単位とは未照合です。

| 工程 | 通信往復 | Redis命令数（Lua内を含む） |
|---|---:|---:|
| 全バックアップ（キー再走査込み） | N＋2S | 4N＋2S |
| 隔離復元・値/期限確認 | 4N | 4N |
| 最小投入・衝突確認・再読取り | 3C | 5C |
| 266作品の配信更新、初回の正常完了 | 20 | 126 |
| 上記に監視接続を加えた1起動 | 22 | 128 |
| 全件旧復旧のための余力 | 少なくとも4N | 少なくとも4N |

隔離復元はEXISTS/RESTORE/DUMP/PTTLの4回/件。元データの期限切れ分は復元対象外です。実Upstashへ隔離DBを作って復元することは行っていません。元DBを復旧先として使う場合の衝突除去・追加走査・認証確認は上記に含まず、追加計上します。監視/読取り/JSON形式の容量・転送も別に見積もります。

例：N=10,000、S=100ならバックアップ40,200命令、隔離復元40,000、旧復旧余力40,000。M=857（作品266＋配信266＋SEO266＋TV59の仮例）ならC=27、投入81往復/135命令。実データのM・N・Sは未計測です。索引不要の復旧経路を仮定し、人物・追加エピソード・監視初期値等は必要分だけ加算します。大きなデータ型のDUMP可否・1通信の制限も未確認です。

時間は `通信往復数/実測処理速度 + バックアップ転送量/実測転送速度 + 再登録/照合 + 作業待機` で求めます。N=10,000、S=100の例のバックアップと全件隔離復元は50,200往復。直列で20〜100往復/秒なら**約8〜42分**で、これは仮定であり実Upstashの測定値ではありません。転送・15分の旧処理待機・目視確認は別。201MBという画面値からDUMP/JSONファイル容量は算出できません。Base64はバイナリより約4/3倍、JSONとキー名も増えます。高速化のため本番に無制限並列接続はしません。

停止時間は、最終バックアップと復元確認を停止後に行う保守案で**数十分〜1時間以上もあり得ます**。実N・接続速度・実データ復元が不明な現時点では、短時間完了を保証しません。無料と確認済みのPC側Redisで事前復元し、停止後は最終差分を検証できる設計へ進めれば短縮できますが、その場合も最後の整合性保証が必要です。
