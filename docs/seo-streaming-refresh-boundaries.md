# 配信情報の更新経路と静的化の境界（2026-11-04）

現行コードを読み取り専用で確認。SEO試験用ブランチでの設計資料であり、本番変更はありません。

## 重要な区別
- **シリーズページの定期更新**：`api/update-streaming.js`。Cron認証あり、`data/streaming-works.json` に列挙された作品を6時・18時（JST）のウィンドウ単位で更新し、Redisの `doko:watch:v3:movie|tv:ID` に見放題 `flatrate` と成功時刻を保存。閲覧者はこのCronを起動しない。
- **個別作品詳細の配信取得**：`api/search.js` の作品ID詳細ルート。作品の固定メタデータは `metadataWithLedger`、配信プロバイダ情報は `getDetailProviders` を使う構成（`WORK_LEDGER_ENABLED==='1'` の場合）。配信キャッシュの `doko:detail-providers:v1:movie|tv:ID` は**約24時間でアクセス時に再取得**する方式で、シリーズページの6時・18時更新と別の保存先・別の更新周期。
- `api/_detail-metadata-cache.js` は共通作品台帳の `extensions.tmdbDetail` に固定情報を保存し、既存APIが要求するTMDB互換の構造を保持する。共通台帳の表層フィールドを一から変換するより、この**既存の固定データ互換形式**を静的JSON生成の候補として先に検証するべき。

## 設計上の判断
1. 「配信情報は6時・18時更新」と一括りにしない。シリーズ用Cronと作品詳細のオンデマンド配信キャッシュは別である。
2. 現在の `detail.html` は固定メタデータと配信データを一体化した `/api/search` レスポンスを描画する。静的固定データを先読みしても、既存APIを引き続き丸ごと呼べば負荷削減にならない。
3. 次の試験は、`extensions.tmdbDetail` を入力にした**固定情報の静的出力**と、**配信のみを安全に返す仕組み**の要件定義。既存の配信キャッシュ、リトライ、エラー表示、レンタル／購入を維持する必要がある。
4. **シリーズ用Cronのキーを個別作品詳細のキーに置き換えない。** 更新頻度・対象作品・保存形式が違う。
5. 実装前に `WORK_LEDGER_ENABLED` の実際の環境設定と `extensions.tmdbDetail` の保存状況を確認。未確認のまま全作品が静的化可能とは判断しない。

## 負荷の見通し
個別作品詳細の初回閲覧で `/api/search` が呼ばれる構造が残る限り、SEO HTML生成だけでは Function 呼び出しはなくならない。固定データと配信データの分離後に、実際のAPI呼び出し回数を比較して削減を確認する。
